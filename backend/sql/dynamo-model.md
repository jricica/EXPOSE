# DynamoDB Model for Feed and Relationships

## Scope

This document defines the DynamoDB model for the social graph and feed subsystem. It is intentionally designed so the backend team can implement and test the logic locally before provisioning AWS resources.

The model covers:

- User relationships: follow, block, mute.
- Feed events: posts, likes, comments, shares, and future social actions.
- Query patterns that must be supported efficiently without scans.

## Design goals

- Query by user without table scans.
- Support reverse lookups for followers and relationship checks.
- Support feed reads with cursor pagination.
- Keep writes predictable and idempotent.
- Allow future expansion to notifications and activity streams.

## Table 1: social_relationships

This table stores directed relationships between two users.

### Item shape

- `pk`: `USER#<sourceUserId>`
- `sk`: `REL#<targetUserId>`
- `gsi1pk`: `USER#<targetUserId>`
- `gsi1sk`: `USER#<sourceUserId>`
- `sourceUserId`: numeric id of the actor.
- `targetUserId`: numeric id of the subject.
- `relationshipType`: `FOLLOW`, `BLOCK`, or `MUTE`.
- `status`: `ACTIVE` or `REMOVED`.
- `createdAt`: ISO timestamp.
- `updatedAt`: ISO timestamp.
- `ttl`: optional expiration for temporary states.

### Why this shape works

The primary partition key groups everything a source user does. The sort key lets us store multiple relationship types if needed. The GSI flips the direction and makes followers and reverse relationship checks efficient.

### Access patterns

1. List all users that I follow.
   - Query `pk = USER#<me>`.

2. List all my followers.
   - Query `gsi1pk = USER#<me>`.

3. Check if I already follow or block another user.
   - Get item by `pk = USER#<me>` and `sk = REL#<targetUserId>`.

4. List all blocked or muted users.
   - Query `pk = USER#<me>` and filter by `relationshipType` if the implementation stores multiple kinds in the same partition.

5. Resolve mutual connections or recommendation signals.
   - Query both directions and compare result sets.

## Table 2: feed_events

This table stores a materialized timeline per feed owner. It is the main read model for the feed.

### Item shape

- `pk`: `FEED#<feedUserId>`
- `sk`: `TS#<normalizedTimestamp>#EVT#<eventId>`
- `gsi1pk`: `ACTOR#<actorUserId>`
- `gsi1sk`: same timestamp-based sort key.
- `gsi2pk`: `ENTITY#<entityType>#<entityId>`
- `gsi2sk`: same timestamp-based sort key.
- `feedUserId`: recipient user id.
- `actorUserId`: user that generated the event.
- `eventType`: `POST_CREATED`, `POST_LIKED`, `POST_COMMENTED`, `POST_SHARED`, `FOLLOWED_USER`, `UNFOLLOWED_USER`.
- `entityType`: `POST`, `USER`, `COMMENT`, or `SHARE`.
- `entityId`: primary entity identifier.
- `parentEntityId`: optional reference for derived actions like comments.
- `payload`: free-form metadata for rendering.
- `visibility`: `PUBLIC`, `FOLLOWERS`, or `PRIVATE`.
- `createdAt`: ISO timestamp.
- `ttl`: optional expiration for ephemeral feed entries.

### Why this shape works

The feed is optimized for reading the timeline of one user. The GSI by actor supports activity views and debugging. The GSI by entity supports fetching all events associated with a post, comment, or share.

### Access patterns

1. Get the latest feed for a user.
   - Query `pk = FEED#<userId>` ordered descending by `sk`.

2. Paginate the feed.
   - Use the last evaluated sort key as a cursor.

3. List activity generated by one actor.
   - Query `gsi1pk = ACTOR#<actorUserId>`.

4. List all events for a post.
   - Query `gsi2pk = ENTITY#POST#<postId>`.

5. Rebuild a user feed after a missed event.
   - Recompute from actor and relationship data, then reinsert the missing feed items.

## Normalized timestamp format

Use a lexicographically sortable timestamp string so the sort key preserves chronology.

Recommended format:

- ISO timestamp sanitized by replacing `:` and `.` with `-`.
- Example: `2026-04-19T18-22-31-123Z`

## Suggested indexes

### social_relationships

- Primary key: `pk`, `sk`
- GSI1: `gsi1pk`, `gsi1sk`

### feed_events

- Primary key: `pk`, `sk`
- GSI1: `gsi1pk`, `gsi1sk`
- GSI2: `gsi2pk`, `gsi2sk`

## Implementation notes

- Relationship writes should be idempotent.
- Feed writes should prefer append-only inserts.
- For fan-out, write one event per recipient feed partition.
- If the system later grows, notification and messaging can reuse the same event model with a different entity type.
- Keep TTL optional until product decides how long feed history must remain queryable.

## Environment variables

- `DYNAMO_RELATIONSHIPS_TABLE`: name of the relationships table.
- `DYNAMO_FEED_TABLE`: name of the feed table.
- `AWS_REGION`: AWS region for the client.

## Local development strategy

- Define the model in TypeScript first.
- Build unit tests around key generation and repository logic.
- Use a local emulator or mocks for integration tests.
- Provision the actual AWS tables only after the model is stable.
